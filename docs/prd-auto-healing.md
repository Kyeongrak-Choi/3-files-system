## 2. 프로젝트 개요

사용자가 사고 싶은 물건과 구매 이유를 입력하면 소비 고민 코칭 API가 LLM 의존 서비스에 분석을 요청하고, 숙고 질문과 소비 점검 결과를 반환한다. LLM 의존 서비스에서 HTTP 429, 타임아웃, 연결 실패·5xx가 발생할 때 Monitor·Diagnosis·Recovery·Verification 역할이 분리된 워크플로로 장애를 탐지하고, 허용된 범위의 복구 또는 대체 응답을 수행한다.

이번 MVP의 목적은 완전한 자율 운영이 아니라, 안전하게 반복 재현할 수 있는 의존 서비스 장애에 대해 제한된 자동 복구와 독립 검증이 동작함을 보여주는 것이다.

## 3. 문제 정의

지름막의 72시간 소비 숙고 흐름에서 코칭 응답은 사용자가 구매 전에 생각을 정리하도록 돕는 핵심 피드백이다. 하지만 LLM 의존 서비스가 사용량 제한, 응답 지연 또는 연결 실패를 일으키면 코칭 요청이 실패하거나 오래 기다리게 된다.

현재는 사용자의 실패 제보나 로그 확인으로 장애를 발견하고, 운영자가 원인을 분류한 뒤 재시도·서비스 상태 확인·대체 응답 여부를 수동으로 결정해야 한다. 이 방식은 탐지와 복구가 늦고, 동일 장애에 대한 재시도 상한과 검증 기준이 일관되지 않으며, 복구가 실제로 성공했는지 Recovery 수행자의 자기보고에 의존한다.

해결할 문제는 다음과 같다.

- LLM 의존 서비스의 허용된 장애를 자동으로 감지하고 유형을 분류한다.
- 제한된 복구 전략을 적용해 사용자 요청을 안전하게 완료하거나 대체 응답을 제공한다.
- 독립 검증으로 정상화를 판정하고, 반복 실패는 자동 중단 후 사람에게 전달한다.
- 장애 주입부터 정상화까지의 근거와 시간을 추적한다.

## 4. 사용자와 이해관계자

### 주요 사용자

- 충동구매를 줄이고 싶은 사용자
- 구매 전에 한 번 더 고민하고 싶은 사용자
- 복잡한 가계부 없이 소비 습관을 돌아보고 싶은 사용자

### 운영 이해관계자

- 장애 사건과 복구 결과를 확인하는 운영 담당자
- 자동 복구 정책과 승인 범위를 검토하는 프로젝트 검토자
- 장애 주입·탐지·복구·검증 결과를 시연하는 교육생 및 평가자

### 사용자 가치

정상 장애 상황에서는 코칭 결과를 지연 또는 실패 없이 받거나, LLM을 사용할 수 없을 때에도 사전 정의된 안전한 대체 안내를 받는다. 운영자는 반복적인 초기 대응을 자동화하고, 사건별 근거와 측정값을 확인할 수 있다.

## 5. 목표와 성공 기준

### 목표

1. HTTP 429, 타임아웃, 연결 실패·5xx, 반복 장애를 안전하게 주입하고 사건으로 기록한다.
2. 장애 유형에 따라 제한된 재시도, 대체 코칭 응답 또는 테스트 환경 복구를 수행한다.
3. Recovery의 성공 보고와 분리된 Verification으로 정상화를 판정한다.
4. 사건별 최대 시도 횟수, 회로 차단, 냉각시간, 사람 에스컬레이션으로 무한 복구 루프를 방지한다.
5. MTTD·MTTR과 복구 근거를 산출할 수 있는 사건 로그를 보존한다.

### 성공 기준

- 최소 3개의 장애 유형이 동일한 실습 환경에서 반복 재현된다.
- 허용된 장애는 사전에 정의된 복구 전략을 최대 3회 이내로 실행한다.
- 복구 성공은 헬스체크와 핵심 코칭 요청·응답 검증을 모두 통과해야 한다.
- 동일 장애가 상한을 넘으면 자동 복구를 중단하고 에스컬레이션한다.
- 모든 데모 사건에 incident_id, trace_id, 탐지·복구·검증 시각, 진단 근거, 최종 상태가 남는다.

## 7. 정상 서비스 시나리오

### 한 문장 정의

> 사용자가 구매 후보와 구매 이유를 요청하면, 서비스는 LLM 의존 서비스에 소비 고민 분석을 요청하고 숙고 질문과 소비 점검 결과를 반환한다.

### 정상 흐름

1. 사용자가 앱에서 물건 이름, 가격, 구매 이유를 입력한다.
2. 소비 고민 코칭 API가 요청 형식과 기본 입력을 확인한다.
3. 코칭 API가 LLM 의존 서비스에 숙고 질문과 소비 점검 결과를 요청한다.
4. 정상 응답을 사용자에게 반환한다.
5. 요청의 사건·추적 정보와 결과 상태를 기록한다.

### 정상 결과

- 사용자 요청에 대응하는 숙고 질문
- 구매 이유와 상황을 점검하는 코칭 결과
- 클라이언트가 처리할 수 있는 유효한 응답 형식

## 8. 장애 시나리오

| 장애 | 발생 위치 | 탐지 신호 | 사용자·운영 영향 | 안전한 재현 방법 | 예상 복구 방향 |
|---|---|---|---|---|---|
| HTTP 429·사용량 초과 | 모의 LLM 의존 서비스 | HTTP 429, quota/rate-limit 근거 | 코칭 응답 실패, 사용량 초과 원인 확인 필요 | 모의 서비스가 429를 반환하도록 설정 | 지수 백오프 재시도 후 대체 응답 |
| 타임아웃 | 모의 LLM 의존 서비스 | 요청 제한시간 초과, 지연 로그 | 사용자가 오래 기다리거나 요청 실패 | 모의 서비스가 제한시간보다 늦게 응답 | 지수 백오프 재시도 후 대체 응답 |
| 연결 실패·5xx | 모의 LLM 의존 서비스 | 연결 오류 또는 HTTP 5xx | 코칭 기능 이용 불가 | 모의 서비스를 중단하거나 5xx 반환 | 재시도, 테스트 환경 재시작 또는 에스컬레이션 |
| 반복 장애 | 동일 의존 서비스·동일 사건 | 연속 실패와 시도 횟수 초과 | 자동 복구가 비용·지연을 키울 수 있음 | 같은 장애를 상한 이상 반복 주입 | 회로 차단 후 사람 에스컬레이션 |

장애 주입은 테스트 환경의 모의 의존 서비스에 한정한다. 실제 운영 데이터, 실제 결제, 실제 사용자 개인정보는 사용하지 않는다.

## 9. 멀티 에이전트 구성

결정적 정책과 상태 전이는 Orchestrator가 관리하며, 역할별 정보 접근과 행동 권한은 분리한다. 모든 역할을 별도 LLM으로 구현해야 하는 것은 아니며 규칙과 함수로 충분한 역할은 결정적 로직으로 구현할 수 있다.

### Monitor Agent

- 책임: 헬스체크·로그·오류율·응답시간을 관찰하고 사건을 생성한다.
- 입력: 헬스체크 결과, API 응답, 애플리케이션 로그, 장애 주입 정보
- 출력: incident_id, trace_id, 발생 시각, 장애 유형 후보, 관찰 근거
- 사용할 수 있는 정보: 조회 전용 상태·로그·지표
- 허용 행동: 상태 조회, 사건 생성
- 금지 행동: 복구 실행, 설정 변경, 재시도 정책 변경
- 실패 시 행동: 관찰 실패를 사건으로 남기고 Orchestrator에 전달한다.

### Diagnosis Agent

- 책임: 관찰 증거를 바탕으로 장애 유형과 원인 후보를 분류한다.
- 입력: 사건 정보, 상태 코드, 오류 로그, 응답시간, 최근 시도 이력
- 출력: 장애 코드, 진단 근거, 신뢰도 또는 규칙 결과, 추천 복구 전략
- 사용할 수 있는 정보: 사건·로그·상태 조회 결과
- 허용 행동: 증거 조회, 분류, 복구안 제안
- 금지 행동: 복구 직접 실행, 정책·시도 상한 변경
- 실패 시 행동: 원인 불명으로 표시하고 자동 변경 없이 사람에게 에스컬레이션한다.

### Recovery Agent

- 책임: Orchestrator가 승인한 허용목록 복구 전략을 실행한다.
- 입력: 승인된 복구 전략, 사건 상태, 현재 시도 횟수
- 출력: 실행 결과, 시도 횟수, 대기시간, 오류 정보
- 사용할 수 있는 정보: 허용된 HTTP 재호출 API, 헬스체크 API, 테스트용 장애 주입·복구 인터페이스
- 허용 행동: 지수 백오프 재시도, 사전 정의된 대체 응답, 테스트 환경의 허용 서비스 재시작
- 금지 행동: 임의 쉘 명령, 허용목록 밖 서비스 조작, 데이터 변경, 인증정보·사용량 한도 변경
- 실패 시 행동: 실행 결과를 기록하고 추가 자동 실행 여부를 Orchestrator에 맡긴다.

### Verification Agent

- 책임: Recovery 결과와 독립적으로 정상화를 검증한다.
- 입력: 복구 결과, 헬스체크, 핵심 코칭 요청 결과, 응답시간·오류율
- 출력: 검증 항목별 결과, 정상화 판정, 실패 근거
- 사용할 수 있는 정보: 검증 전용 헬스체크와 핵심 기능 요청
- 허용 행동: 헬스체크·기능 검증·회귀 검증
- 금지 행동: 검증 없이 성공 선언, 복구 정책 변경
- 실패 시 행동: 사건을 실패 또는 재시도 가능 상태로 남기고 Orchestrator에 전달한다.

### Orchestrator

- 책임: 사건 상태, 역할 호출 순서, 정책, 시도 상한, 타임아웃, 회로 차단과 에스컬레이션을 관리한다.
- 입력: Monitor·Diagnosis·Recovery·Verification 결과
- 출력: 다음 역할 호출, 사건 상태 전이, 최종 결과
- 사용할 수 있는 정보: 정책, 허용목록, 사건 이력, 각 역할의 결과
- 허용 행동: 정의된 순서대로 역할 호출, 정책에 따른 재시도·중단·에스컬레이션
- 금지 행동: 진단 근거 없는 직접 복구, 정책 우회, 시도 횟수 증가
- 실패 시 행동: 안전 중단하고 Notification을 통해 사건을 전달한다.

### Notification Agent

- 책임: 사건 상태와 증거를 사람에게 보고하고 승인을 요청한다.
- 입력: 사건 정보, 진단·복구·검증 결과
- 출력: 알림, 에스컬레이션, 승인 요청 결과
- 사용할 수 있는 정보: 사건 요약과 비민감 증거
- 허용 행동: 보고와 승인 요청
- 금지 행동: 복구 정책 임의 변경, 승인 없는 복구 실행
- 실패 시 행동: 알림 실패를 사건에 기록하고 별도 수동 확인 대상으로 남긴다.

## 10. 에이전트 협업 흐름

    [장애 주입 또는 장애 발생]
              ↓
    [Monitor: 신호 관찰·사건 생성]
              ↓
    [Diagnosis: 장애 분류·근거·복구안 제안]
              ↓
    [Orchestrator: 정책·권한·시도 상한 확인]
              ↓
    [Recovery: 허용된 재시도·대체 응답·테스트 복구]
              ↓
    [Verification: 헬스체크·핵심 코칭 요청 독립 검증]
           ┌──┴──┐
        성공   실패
           ↓      ↓
    [정상화 기록] [상한 확인]
                      ├─ 재시도 가능 → Recovery
                      └─ 상한 초과/원인 불명 → 회로 차단·Notification

| 타임아웃 | 제한시간 초과 | timeout 로그와 응답시간 | 지수 백오프 재시도 | 대체 코칭 응답 | 3회 | 불필요 | 추가 호출 중단 | 제한시간 내 핵심 요청 |
| 연결 실패·5xx | 연결 오류 또는 5xx | 네트워크 오류·상태 코드 | 지수 백오프 재시도 | 테스트 모의 서비스 재시작 또는 에스컬레이션 | 3회 | 테스트 재시작은 불필요 | 재시작 실패 시 자동 중단 | 헬스체크·핵심 요청 |
| 반복 장애 | 동일 실패 누적 | 사건 이력과 시도 횟수 | 추가 자동 복구 제한 | 회로 차단·사람 에스컬레이션 | 3회 | 에스컬레이션 필요 | 자동 실행 중단 | 차단 상태·알림 확인 |

기본 재시도 간격은 1초, 2초, 4초의 지수 백오프로 한다. 실제 API 타임아웃과 회로 차단 냉각시간은 [미결정]이다. 동일 사건에서 최대 3회 실패하면 회로를 차단하고, 재개 조건이 충족되기 전까지 자동 복구를 수행하지 않는다.

## 12. 자율성과 Human-in-the-loop

### 자동 실행 가능

- 단일 코칭 요청에 대한 최대 3회의 지수 백오프 재시도
- 사전 정의된 대체 코칭 응답 반환
- 테스트 환경의 허용목록에 포함된 모의 의존 서비스 재시작
- 헬스체크·핵심 기능 검증과 사건 기록

### 사람 승인 후 실행

- LLM 사용량 한도·요금제 변경
- 운영 라우팅·운영 설정 변경
- 운영 환경 서비스 재시작 또는 다수 사용자에게 영향을 주는 조치
- [미결정] 승인 타임아웃과 승인자

미승인 또는 승인 타임아웃 시 자동 변경 없이 안전 중단하고 사건을 에스컬레이션한다.

### 자동 실행 금지

- 임의 쉘 명령 생성·실행
- 허용목록 밖 서비스 조작
- 운영 데이터베이스 변경·삭제
- 인증정보·권한 변경
- 비용 제한 없는 인프라 확장
- 원인 불명 상태에서의 자동 변경

### 잘못된 복구 처리

MVP에서는 데이터·운영 설정 변경을 자동 실행하지 않으므로 복잡한 롤백 대신 안전 중단을 기본으로 한다. 테스트 서비스 재시작을 수행할 때는 실행 파라미터와 이전 상태를 기록하며, Verification 실패 시 추가 자동 복구를 중단한다.

## 13. 기능 요구사항

### FR-001 소비 고민 코칭 요청

- 설명: 사용자의 구매 후보와 구매 이유를 받아 코칭 요청을 생성한다.
- 입력: 물건 이름, 가격, 구매 이유 또는 이에 준하는 최소 입력
- 기대 동작: LLM 의존 서비스에 코칭 요청을 전달하고 결과를 반환한다.
- 예외 상황: 입력 오류는 코칭 의존 서비스 호출 전에 거부한다.
- 인수조건: 정상 입력에 대해 클라이언트가 처리할 수 있는 코칭 응답이 반환된다.

### FR-002 의존 서비스 장애 주입

- 설명: 테스트 환경에서 정의된 장애 유형을 안전하게 재현한다.
- 입력: 장애 유형과 주입 상태
- 기대 동작: 모의 LLM 의존 서비스가 HTTP 429, 지연, 연결 실패·5xx 또는 반복 장애를 재현한다.
- 예외 상황: 허용되지 않은 장애 유형이나 운영 대상 지정은 거부한다.
- 인수조건: 최소 3개 장애 유형이 반복 주입되고 각 사건에 주입 시각이 기록된다.

### FR-003 장애 사건 생성 및 탐지

- 설명: Monitor가 장애 신호를 관찰하고 사건을 생성한다.
- 입력: 상태 코드, 오류, 응답시간, 헬스체크 결과
- 기대 동작: 사건 식별자·추적 식별자와 탐지 근거를 기록한다.
- 예외 상황: 관찰 정보가 부족하면 원인 미확정 사건으로 남긴다.
- 인수조건: 장애 주입 후 탐지 시각과 근거를 확인할 수 있다.

### FR-004 장애 진단

- 설명: Diagnosis가 증거를 기반으로 장애 유형을 분류하고 복구안을 제안한다.
- 입력: 사건·로그·상태 코드·시도 이력
- 기대 동작: 장애 코드와 판단 근거를 반환한다.
- 예외 상황: 원인을 판단할 수 없으면 자동 변경 없이 에스컬레이션한다.
- 인수조건: 정의된 장애 유형별 진단 근거가 사건에 남는다.

### FR-005 제한된 복구 실행

- 설명: Recovery가 승인된 복구 전략만 실행한다.
- 입력: 복구 전략, 사건 ID, 현재 시도 횟수
- 기대 동작: 재시도·대체 응답·테스트 재시작 중 허용된 행동을 수행한다.
- 예외 상황: 상한 초과, 허용목록 외 행동, 권한 부족은 실행하지 않는다.
- 인수조건: 모든 복구 시도와 결과가 기록되고 최대 3회를 넘지 않는다.

### FR-006 회로 차단과 에스컬레이션

- 설명: 반복 실패 또는 원인 불명 장애의 자동 복구를 중단한다.
- 입력: 연속 실패 이력, 시도 횟수, 진단 결과
- 기대 동작: 회로를 차단하고 Notification을 통해 사람에게 사건을 전달한다.
- 예외 상황: 알림 실패도 사건에 기록한다.
- 인수조건: 동일 장애가 상한을 넘으면 추가 Recovery 호출이 발생하지 않는다.

### FR-007 독립 복구 검증

- 설명: Verification이 Recovery와 독립적으로 정상화를 판정한다.
- 입력: 헬스체크, 핵심 코칭 요청, 응답시간·오류율
- 기대 동작: 검증 항목별 결과와 최종 정상·실패 상태를 기록한다.
- 예외 상황: 일부 항목 실패 시 정상화를 선언하지 않는다.
- 인수조건: 헬스체크·핵심 요청·응답 스키마 검증을 통과해야 복구 성공으로 기록된다.

### FR-008 사건 추적 및 측정

- 설명: 사건의 전 생명주기와 장애 대응 시간을 기록한다.
- 입력: 주입·탐지·복구·검증 이벤트
- 기대 동작: MTTD, MTTR, 시도 횟수, 최종 상태를 산출할 수 있게 한다.
- 예외 상황: 시각 또는 식별자가 누락되면 불완전 사건으로 표시한다.
- 인수조건: 데모 사건별로 injected_at, detected_at, recovery_started_at, recovered_at을 확인할 수 있다.

## 14. 비기능 요구사항

### NFR-001 안전성

자동 복구는 테스트 환경의 허용목록과 사전 정의된 전략으로 제한한다. 임의 명령, 운영 데이터 변경, 인증정보 변경은 실행할 수 없어야 한다.

### NFR-002 신뢰성

복구 성공은 Recovery 결과만으로 확정하지 않으며, 독립 Verification이 핵심 기능과 응답 형식을 확인해야 한다.

### NFR-003 재현성

동일 장애 주입 조건으로 최소 3개 장애 유형을 반복 실행할 수 있어야 한다. 장애 주입 상태와 시각을 사건에 기록한다.

### NFR-004 관측 가능성

사건 ID, 추적 ID, 탐지·진단·복구·검증 근거, 시도 횟수, 최종 상태를 조회할 수 있어야 한다.

### NFR-005 무한 루프 방지

사건별 최대 시도 횟수는 3회이며, 동일 전략 반복 제한, 회로 차단, 냉각시간, 전체 워크플로 타임아웃을 적용한다. 정확한 타임아웃과 냉각시간은 [미결정]이다.

### NFR-006 데이터 보호

실제 개인정보·운영 데이터를 사용하지 않는다. 사용자 식별자, 토큰, 원문 구매 메모는 로그에서 제외하거나 마스킹·해시 처리한다.

### NFR-007 설명 가능성

장애 유형과 복구 전략을 선택한 근거를 사건에 남겨 사람이 사후 검토할 수 있어야 한다.

## 16. 검증 및 완료 기준

### 복구 성공 판정

다음 조건을 모두 만족할 때만 정상화로 판정한다.

- 의존 서비스 헬스체크가 정상 응답한다.
- 핵심 코칭 요청이 정의된 제한시간 안에 성공한다.
- 코칭 응답 스키마가 유효하다.
- 오류율과 응답시간이 실험 기준선으로 돌아온다.
- Verification이 독립 검증 결과를 기록한다.

### 측정 지표

- MTTD = detected_at - injected_at
- MTTR = recovered_at - injected_at
- 복구 실행시간 = recovered_at - recovery_started_at
- 복구 성공률 = 자동 정상화 건수 ÷ 전체 장애 건수
- 평균 복구 시도 = 전체 시도 횟수 ÷ 성공 건수
- 에스컬레이션율 = 에스컬레이션 건수 ÷ 전체 장애 건수
- 회귀 테스트 통과율 = 통과 검증 건수 ÷ 전체 검증 건수

### Day 3 데모 검증 순서

1. 정상 코칭 요청 기준선 확인
2. HTTP 429·사용량 초과 주입 및 복구 확인
3. 타임아웃 주입 및 복구 확인
4. 연결 실패·5xx 주입 및 테스트 복구 또는 에스컬레이션 확인
5. 동일 장애 반복 주입 및 회로 차단 확인
6. 자동 복구 실패 후 사람 에스컬레이션 확인

## PRD 자체 검토 결과

### 충족 항목

- 서비스, 사용자, 정상 결과와 중단 영향이 정의되어 있다.
- 최소 3개의 재현 가능한 장애와 장애별 복구 방향이 정의되어 있다.
- Monitor·Diagnosis·Recovery·Verification 역할과 Orchestrator·Notification의 경계가 정의되어 있다.
- 자동 실행, 사람 승인, 자동 실행 금지 행동이 구분되어 있다.
- 재시도 상한, 회로 차단, 안전 중단, 에스컬레이션이 정의되어 있다.
- 독립 검증, MTTD·MTTR, 필수 로그와 Day 3 데모가 정의되어 있다.
- 3일 MVP 포함·제외 범위와 기능·비기능 요구사항이 명시되어 있다.

### 보완이 필요한 항목

- 실제 타임아웃, 냉각시간, 로그 저장 위치와 보존 기간은 구현 전에 결정해야 한다.
- 대체 코칭 응답의 최종 문구와 응답 스키마를 확정해야 한다.
- 승인자와 PRD 검토자를 지정해야 한다.

### 범위 초과 위험

- 실제 LLM·로그인·운영 인프라를 붙이려는 요구가 추가되면 3일 MVP 범위를 초과할 수 있다.
- 에이전트를 모두 LLM 기반으로 구현하려 하면 결정적 규칙과 상태기계보다 복잡도가 커질 수 있다.
