# 1. 서비스 선정

## 1.0 후보 서비스 비교

| 후보 서비스 | 핵심 기능 | 주요 장애 | Auto Healing 적합성 | 선정 결과 |
|---|---|---|---|---|
| 소비 고민 코칭 API | 구매 후보와 이유를 분석해 숙고 질문·점검 결과 생성 | LLM 사용량 초과, 타임아웃, 연결 실패 | 매우 높음 | 선정 |
| 구매 기록 요약 API | 누적 구매 고민 기록을 요약해 소비 회고 결과 생성 | LLM 사용량 초과, 타임아웃, 응답 형식 오류 | 높음 | 후속 후보 |
| 소비 패턴 분석 API | 구매 기록에서 반복 소비 패턴 분석 | LLM 사용량 초과, 분석 지연 | 높음 | 범위 확장 후보 |
| 알림 문구 생성 API | 72시간 만료 알림 문구 생성 | LLM 장애, 알림 지연 | 중간 | 제외 |

**선정 근거:** 3일 MVP에서는 사용자 요청과 장애 주입의 인과관계가 명확한 소비 고민 코칭 API를 대상으로 한다. 구매 기록 요약 API는 기존 기록이 누적된 뒤 회고·요약을 제공하는 후속 후보로 함께 정의한다.

## 1.1 어떤 서비스의 장애를 자동 복구할 것인가?

**서비스 이름:** 소비 고민 코칭 API

**한 문장 설명:**

> 사용자가 사고 싶은 물건과 구매 이유를 등록하면, 서비스는 LLM을 활용해 숙고 질문과 소비 점검 결과를 생성하고 반환한다.

**정상 실행 흐름:**

```text
사용자(Flutter 앱)
  ↓
[FastAPI 소비 고민 코칭 API]
  ↓
[LLM API 모의 또는 외부 의존 서비스]
  ↓
정상 결과: [숙고 질문·소비 점검 결과·코칭 응답]
```

**핵심 의존 서비스:**

| 의존 대상 | 용도 | 실패 시 영향 | 모의 구현 여부 |
|---|---|---|---|
| LLM API | 구매 고민 분석 및 코칭 응답 생성 | 코칭 응답 생성 실패·지연 | 실습용 장애 주입 모의 구현 권장 |
| 기록 저장소 | 구매 후보·코칭 결과 저장 | 기록 조회·저장 실패 | [미결정] |

**후속 후보 서비스:** 구매 기록 요약 API — 누적된 구매 고민 기록을 LLM으로 요약해 사용자의 소비 회고 결과를 제공한다. 본 MVP의 자동 복구 대상에는 포함하지 않는다.

## 1.2 서비스가 멈추면 어떤 영향이 발생하는가?

### 사용자 영향

- 구매 고민 등록 후 코칭 응답을 받지 못한다.
- 72시간 숙고 과정의 피드백이 지연되거나 중단된다.

### 운영 영향

- LLM 사용량 초과, 지연, 연결 실패를 운영자가 확인해야 한다.
- 반복 재시도에 따른 비용·쿼터 소진 가능성이 있다.

### 데이터·비용·보안 영향

- 실습 MVP는 실제 결제·개인정보·운영 DB를 처리하지 않는다.
- 무제한 재시도로 LLM 비용과 사용량이 증가할 수 있다.
- 프롬프트와 응답 로그에는 민감정보를 저장하지 않도록 한다.

### 심각도

- [x] 중간 — 일부 요청이 실패하고 운영자 대응이 필요함

**선택 근거:** 결제나 금전 거래를 직접 수행하지는 않지만, 핵심 코칭 기능이 중단되고 LLM 사용량 및 비용에 영향을 준다.

## 1.3 현재 사람은 장애를 어떻게 발견하고 복구하는가?

| 단계 | 현재 사람의 행동 | 사용하는 정보·도구 | 소요시간 | 문제점 |
|---|---|---|---:|---|
| 탐지 | 사용자의 실패 제보 또는 로그 확인 | 앱 오류, 서버 로그 | [미결정] | 사전 탐지가 어렵다 |
| 진단 | LLM 응답 코드·지연·사용량 확인 | FastAPI 로그, LLM 콘솔 | [미결정] | 원인 분류가 수동이다 |
| 복구 | 재시도, 대체 응답, 사용량 확인 | API 설정·운영 콘솔 | [미결정] | 일관된 상한·정책이 없다 |
| 검증 | 코칭 API 재호출 및 결과 확인 | 헬스체크·기능 요청 | [미결정] | 복구자의 자기보고에 의존한다 |
| 보고 | 실패 원인과 조치 기록 | 이슈·메신저 | [미결정] | 사건 정보가 분산된다 |

**자동화하려는 단계:** 탐지, 장애 유형 진단, 제한된 재시도, 허용된 대체 응답, 독립 검증, 사건 기록

**사람이 계속 담당해야 할 단계:** 원인 불명 장애, 사용량·비용 정책 변경, 실제 운영 설정 변경, 반복 실패 후 최종 판단

# 2. 에이전트 설계

## 2.1 장애를 탐지하는 주체는 누구인가?

**에이전트 이름:** Monitor

**관찰 데이터:** 헬스체크 응답, 애플리케이션 로그, 오류율, 응답시간, LLM API 상태 코드

**장애 판정 조건:** 허용된 상태 코드가 아닌 응답, 타임아웃, 연속 오류 임계치 초과

**출력 메시지:** incident_id, 서비스, 장애 유형 후보, 발생 시각, 관찰 근거

## 2.2 원인을 진단하는 주체는 누구인가?

**에이전트 이름:** Diagnosis

**입력:** 사건 정보, 상태 코드, 오류 로그, 응답시간, 최근 시도 이력

| 장애 코드 | 설명 | 판단 근거 | 신뢰도 또는 규칙 |
|---|---|---|---|
| LLM_QUOTA | LLM 사용량 초과 또는 제한 | HTTP 429, quota/rate-limit 근거 | 규칙 기반 |
| LLM_TIMEOUT | LLM 응답 지연 | 제한시간 초과 | 규칙 기반 |
| LLM_UNAVAILABLE | 연결 실패·5xx | 네트워크 오류 또는 HTTP 5xx | 규칙 기반 |

**원인을 판단할 수 없을 때 행동:** 자동 변경을 중단하고 Notification을 통해 사람에게 에스컬레이션

## 2.3 복구를 실행하는 주체는 누구인가?

**에이전트 이름:** Recovery

**허용된 복구 행동:** 제한된 지수 백오프 재시도, 사전 정의된 대체 코칭 응답 반환, 테스트 환경의 허용목록 서비스 재시작

**금지된 행동:** 임의 쉘 명령 실행, 허용목록 밖 서비스 조작, 운영 데이터 변경, 인증정보·사용량 한도 변경

**필요한 도구·API·명령:** 허용된 HTTP 재호출 API, 헬스체크 API, 사전 정의된 로컬 장애 주입·복구 인터페이스

## 2.4 복구 성공을 독립적으로 검증하는 주체는 누구인가?

**에이전트 이름:** Verification

**독립성이 필요한 이유:** Recovery의 성공 보고만으로 정상화를 선언하면 같은 장애가 남아 있어도 완료 처리할 수 있기 때문이다.

**검증 항목:** 헬스체크 정상, 핵심 기능 테스트 통과, 오류율 정상 범위, 응답시간 정상 범위, 회귀 테스트 통과

**복구 실패 판정 조건:** 제한된 재시도 후 코칭 API가 정상 응답하지 않거나 검증용 핵심 요청이 실패함

## 2.5 오케스트레이터가 필요한가?

- [x] 필요함

**판단 근거:** 탐지→진단→복구→검증 순서, 시도 횟수, 타임아웃, 에스컬레이션을 일관되게 관리해야 한다.

### 오케스트레이터의 책임

- 사건 상태와 역할 호출 순서 관리
- 재시도·회로 차단·전체 타임아웃 관리
- 성공·실패·에스컬레이션 상태 전환

### 오케스트레이터가 해서는 안 되는 일

- 진단 근거 없이 직접 복구 실행
- 정책과 허용목록을 우회하거나 시도 횟수를 늘리는 일

## 2.6 에이전트 협업 구조

| 에이전트 | 입력 | 출력 | 호출 주체 | 허용 권한 | 타임아웃 |
|---|---|---|---|---|---:|
| Monitor | 헬스체크·로그·지표 | 사건 생성 | Orchestrator | 조회·사건 생성 | [미결정] |
| Diagnosis | 사건·증거 | 장애 분류·복구안 | Orchestrator | 증거 조회·제안 | [미결정] |
| Recovery | 승인된 복구안 | 실행 결과 | Orchestrator | 허용목록 복구 | [미결정] |
| Verification | 복구 결과·기능 요청 | 검증 결과 | Orchestrator | 헬스체크·기능 검증 | [미결정] |
| Notification | 사건 상태·증거 | 사람 알림·에스컬레이션 | Orchestrator | 보고·승인 요청 | [미결정] |

### 협업 흐름

```text
[장애 발생]
  ↓
[Monitor: 탐지·사건 생성]
  ↓
[Diagnosis: 장애 분류·복구안 제안]
  ↓
[Orchestrator: 정책 확인 및 Recovery 호출]
  ↓
[Recovery: 제한된 재시도 또는 대체 응답]
  ↓
[Verification: 헬스체크·핵심 기능 독립 검증]
  ├─ 성공 → [정상화 기록·Notification 보고]
  └─ 실패 → [재시도 상한 확인 후 회로 차단·사람 에스컬레이션]
```

# 3. 자율성과 통제

## 3.1 자동으로 실행해도 되는 복구

| 복구 행동 | 자동 허용 이유 | 영향 범위 | 선행조건 | 실행 후 검증 |
|---|---|---|---|---|
| 지수 백오프 재시도 | 일시적 제한·네트워크 오류에 한정 | 단일 코칭 요청 | 장애 유형이 허용 목록에 있음 | 핵심 코칭 요청 |
| 대체 코칭 응답 | 사용자 요청을 안전하게 완료 | 해당 요청 1건 | LLM 실패·대체 문구 사전 정의 | 응답 스키마·상태 확인 |
| 테스트 의존 서비스 재시작 | 로컬 실습 환경에서만 허용 | 모의 서비스 | 허용목록·사전 상태 저장 | 헬스체크·기능 검증 |

## 3.2 사람의 승인이 필요한 복구

| 복구 행동 | 승인 필요 이유 | 승인자 | 승인 타임아웃 | 미승인 시 행동 |
|---|---|---|---:|---|
| LLM 사용량 한도·요금제 변경 | 비용 발생·운영 정책 변경 | 운영 담당자 | [미결정] | 자동 변경 없이 에스컬레이션 |
| 실제 운영 설정·라우팅 변경 | 다수 사용자 영향 | 운영 담당자 | [미결정] | 안전 중단·알림 |

## 3.3 복구를 몇 번까지 재시도할 것인가?

**최대 시도 횟수:** 3회

**대기 방식:** 지수 백오프

**대기시간:** 1초, 2초, 4초를 기본안으로 하며 실제 구현 전 검토

**시도 횟수를 저장할 위치:** incident_id 기준 사건 상태와 로그

## 3.4 무한 복구 루프 방지

- [x] 장애별 최대 시도 횟수
- [x] 같은 전략 반복 제한
- [x] 회로 차단기
- [x] 냉각시간
- [x] 전체 워크플로 타임아웃
- [x] 사람 에스컬레이션

**회로 차단 조건:** 동일 사건의 복구 실패 3회 또는 연속 동일 장애 임계치 초과

**회로 재개 조건:** 냉각시간 후 사람 확인 또는 새 사건으로 재평가

## 3.5 잘못된 복구 취소

MVP에서는 데이터 변경·운영 설정 변경을 자동 실행하지 않으므로 복잡한 롤백 대신 안전 중단을 기본으로 한다. 테스트 환경 서비스 재시작 전에는 실행 파라미터와 상태를 기록하고, 검증 실패 시 추가 자동 복구를 중단한다.

## 5.1 복구 성공 판정 지표

| 회귀 테스트 | 기존 정상 흐름 통과 | 검증 실행 결과 | 실패 |

## 5.2 시간 측정

```text
injected_at  = 장애 주입 시각
detected_at  = Monitor가 사건을 생성한 시각
recovery_started_at = Recovery 실행 시작 시각
recovered_at = Verification이 정상화를 확인한 시각
```

```text
MTTD = detected_at - injected_at
MTTR = recovered_at - injected_at
복구 실행시간 = recovered_at - recovery_started_at
```

**시간을 기록할 컴포넌트:** Orchestrator와 각 역할의 사건 로그

**시간 형식과 타임존:** ISO 8601, UTC 기준 권장 [최종 결정 필요]

# 7. 최종 범위 선언

## 반드시 구현할 것

1. 구매 고민 코칭 요청과 LLM 의존 서비스의 최소 흐름
2. HTTP 429·타임아웃·연결 실패를 포함한 장애 주입·탐지·복구 흐름
3. 재시도 상한·회로 차단·독립 검증·사건 로그

## 구현하지 않을 것

1. 실제 결제·금융·쇼핑몰 연동
2. Google·카카오 로그인 신규 구현 및 인증 장애 자동복구
3. 운영 DB 변경, 무제한 비용 확장, 임의 명령 자동 실행

## 성공 기준

1. 최소 3개 장애 유형이 반복 재현된다.
2. 허용된 장애는 제한된 자동 복구 또는 대체 응답으로 처리되고 검증된다.
3. 반복 실패는 회로 차단되고 사람에게 에스컬레이션되며 MTTD·MTTR을 산출할 수 있다.

## 주요 위험과 대응

| 위험 | 가능성 | 영향 | 대응 |
|---|---|---|---|
| 실제 LLM 사용량·비용 초과 | 중간 | 높음 | 모의 LLM 사용, 호출 상한, 대체 응답 |
| 에이전트 역할 중복 | 중간 | 중간 | Monitor·Diagnosis·Recovery·Verification 권한 분리 |
