## 5. 아이디에이션 시작 예시

### 관심 분야가 있는 경우

```text
서비스 선정 아이디에이션을 시작해 주세요.

- 관심 분야: 예약 및 일정 관리
- 사용할 수 있는 기술: Python, FastAPI, Docker
- 개발 인원: 3명
- 실행환경: 개인 노트북
- 경험한 문제: 외부 예약 API가 느리거나 실패하면 전체 예약 요청이 실패함

아직 서비스를 확정하지 않았습니다.
먼저 필요한 질문을 해 주세요.
```

### 아이디어가 없는 경우

```text
서비스 아이디어가 아직 없습니다.
3일 안에 구현할 수 있고, 최소 3개의 장애를 안전하게 재현할 수 있으며,
Auto Healing의 필요성을 보여줄 수 있는 후보를 찾고 싶습니다.
한 번에 최대 5개의 질문으로 서비스 선정을 진행해 주세요.
```

서비스는 다음 구조로 설명할 수 있어야 한다.

```text
사용자 → 핵심 요청 → 핵심 서비스 → 의존 서비스 → 정상 결과
```

예시 후보:

- 예약 API → 일정 조회 모의 서비스
- 알림 API → 메시지 전송 모의 서비스
- 파일 처리 API → 파일 변환 모의 서비스
- 데이터 수집 API → 외부 데이터 모의 서비스
- 주문 API → 재고 조회 모의 서비스

예시는 정답이 아니다. 구조만 참고한다.

# 6. 실습 진행 방법

## 단계 1. 서비스 선정

### 목표

3일 동안 안전하게 구현하고 장애를 반복 재현할 수 있는 최소 서비스 하나를 선정한다.

### 핵심 질문

1. 어떤 서비스의 장애를 자동 복구할 것인가?
2. 주요 사용자는 누구인가?
3. 사용자는 무엇을 요청하고 어떤 결과를 받는가?
4. 핵심 서비스는 어떤 의존 서비스와 연결되는가?
5. 서비스가 멈추면 사용자와 운영조직에 어떤 영향이 발생하는가?
6. 현재 사람은 장애를 어떻게 발견하고 복구하는가?
7. 3일 안에 구현할 최소 범위는 무엇인가?

### 나쁜 예

> 쇼핑몰을 자동 복구한다.

서비스 범위와 장애 위치가 불명확하고 3일 안에 검증하기 어렵다.

### 좋은 예

> 사용자가 예약 API에 가능 시간 조회를 요청하면 예약 API는 일정 조회 모의 서비스에서 가능한 시간을 확인해 반환한다. 일정 조회 서비스가 실패하거나 지연되면 복구 워크플로가 장애를 탐지하고 제한된 복구 후 정상화 여부를 독립 검증한다.

### 후보 평가 기준

| 기준 | 확인 질문 |
|---|---|
| 문제 명확성 | 사용자와 실패 상황을 한 문장으로 설명할 수 있는가? |
| 장애 재현성 | 격리 환경에서 반복 주입할 수 있는가? |
| Auto Healing 필요성 | 자동 탐지·복구가 의미 있는가? |
| 3일 구현 가능성 | 최소 서비스로 구현할 수 있는가? |
| 데이터 안전성 | 실제 결제·개인정보 없이 실습 가능한가? |
| 역할 분리 | 탐지·진단·복구·검증 분리가 의미 있는가? |
| 검증 가능성 | 복구 성공을 수치나 테스트로 판정할 수 있는가? |

### 권장 장애 유형

최소 3개를 선택한다.

1. 의존 API의 일시적 `HTTP 5xx`
2. 응답 지연과 타임아웃
3. 서비스 연결 실패
4. 프로세스·컨테이너 중단
5. 잘못된 설정
6. 동일 장애 반복

제외 대상:

- 실제 데이터 삭제
- 실제 결제·개인정보 처리
- 운영 DB 파괴
- 비용 제한 없는 클라우드 확장
- LLM이 생성한 임의 명령의 자동 실행

### 완료 체크

- [ ] 서비스가 한 문장으로 정의됐다.
- [ ] 사용자·정상 결과·의존 서비스가 식별됐다.
- [ ] 최소 3개의 장애를 안전하게 재현할 수 있다.
- [ ] MVP 포함·제외 범위가 구분됐다.
- [ ] 데이터 손상 없이 반복 실험할 수 있다.

### 승인 게이트

Codex가 다음을 질문해야 한다.

> 이 서비스를 Auto Healing 프로젝트의 PRD 대상으로 확정할까요?

교육생이 명시적으로 승인한 후 단계 2로 넘어간다.

## 단계 2. 에이전트 개념 설계

### 목표

장애 대응 역할의 책임·입력·출력·권한을 정의한다.

| 역할 | 책임 | 허용 행동 | 금지 행동 |
|---|---|---|---|
| Monitor | 상태·로그·지표 관찰 | 조회, 사건 생성 | 설정 변경·복구 실행 |
| Diagnosis | 장애 유형과 원인 후보 판단 | 증거 조회, 복구안 제안 | 복구 직접 실행 |
| Recovery | 승인된 복구전략 실행 | 제한된 재시도·재시작·롤백 | 임의 명령·데이터 삭제 |
| Verification | 복구 결과 독립 검증 | 헬스체크·기능 검증 | 검증 없는 완료 선언 |
| Orchestrator | 상태·순서·시도 제한 관리 | 역할 호출·에스컬레이션 | 정책 우회·직접 조작 |
| Notification | 사람에게 결과 전달 | 승인 요청·증거 보고 | 복구정책 임의 변경 |

> 모든 역할을 별도 LLM 에이전트로 구현할 필요는 없다. 규칙·함수·상태기계로 충분한 역할은 별도 에이전트로 분리하지 않는다.

### 설계 질문

- 별도 역할로 분리할 근거는 무엇인가?
- 입력과 출력은 무엇인가?
- 어떤 정보와 도구에 접근하는가?
- 어떤 행동을 금지하는가?
- 판단 불가 또는 실패 시 누구에게 넘기는가?

### 핵심 원칙

- 탐지·진단·복구·검증을 한 역할에 모두 맡기지 않는다.
- Recovery의 성공 보고만으로 복구 완료를 선언하지 않는다.
- 독립 검증 단계가 정상화 여부를 확인한다.
- Orchestrator는 재시도와 권한 제한을 우회할 수 없다.
- 원인 불명 장애는 자동 변경 없이 사람에게 넘긴다.

### 개념적 사건 정보 예시

```json
{
  "incident_id": "INC-001",
  "service": "example-service",
  "failure_type": "HTTP_500",
  "severity": "medium",
  "evidence": ["health check returned 500"],
  "attempt": 1,
  "recommended_action": "retry_with_backoff",
  "requires_human_approval": false
}
```

필드명은 예시이며 실제 스키마는 상세 설계 단계에서 확정한다.

### 완료 체크

- [ ] 역할별 책임·입력·출력이 정의됐다.
- [ ] 접근 정보와 도구가 정의됐다.
- [ ] 허용 행동과 금지 행동이 구분됐다.
- [ ] 복구와 검증 역할이 분리됐다.
- [ ] 원인 불명 장애 처리 방식이 있다.

## 단계 3. 자율성과 통제

### 자동 실행 후보

- 제한된 재시도와 지수 백오프
- 헬스체크 재실행
- 테스트 환경의 허용목록 기반 재시작
- 사전에 승인된 대체 경로

### 사람 승인 필요 후보

- 운영 설정 변경
- 버전 롤백
- 데이터 수정·삭제
- 비용이 발생하는 인프라 확장
- 개인정보·결제·권한 관련 변경
- 여러 서비스에 영향을 주는 조치

### 자동 실행 금지 후보

- LLM이 임의로 생성한 쉘 명령
- 허용목록 밖의 서비스 재시작
- 운영 데이터베이스 변경
- 인증정보 변경
- 비용 한도가 없는 리소스 생성

### 재시도 정책 예시

```yaml
max_attempts: 3
backoff_seconds: [1, 2, 4]
cooldown_seconds: 30
circuit_breaker:
  failure_threshold: 3
  reset_timeout_seconds: 60
```

수치는 예시이며 서비스 영향도와 실습환경에 맞는 근거를 제시해야 한다.

### 무한 루프 방지

1. 사건별 시도 횟수를 기록한다.
2. 동일 전략을 상한 이상 반복하지 않는다.
3. 연속 실패 시 회로를 차단한다.
4. 회로가 열린 동안 자동 복구를 중단한다.
5. 전체 워크플로에 타임아웃을 둔다.
6. 실패 이력과 추천 행동을 사람에게 전달한다.

### 잘못된 복구 처리

| 복구 행동 | 사전 상태 | 실패 시 대응 |
|---|---|---|
| 설정 변경 | 기존 설정 | 기존 설정 복원 |
| 새 버전 배포 | 이전 버전 | 이전 버전 재배포 |
| 대체 API 전환 | 기존 라우팅 | 기존 라우팅 복원 |
| 프로세스 재시작 | 실행 파라미터·이전 상태 | 자동 복구 중단·에스컬레이션 |

### 완료 체크

- [ ] 자동 실행·사람 승인·실행 금지 행동이 구분됐다.
- [ ] 재시도 상한이 정해졌다.
- [ ] 회로 차단과 재개 조건이 있다.
- [ ] 롤백 또는 안전 중단 방법이 있다.
- [ ] 실패 후 에스컬레이션 정보가 정의됐다.

## 단계 4. 검증 설계

### 목표

복구 성공을 에이전트의 자기보고가 아닌 측정값과 독립 검증으로 판단한다.

| 지표 | 의미 | 측정 방법 |
|---|---|---|
| MTTD | 장애 발생부터 탐지까지 | `detected_at - injected_at` |
| MTTR | 장애 발생부터 정상화까지 | `recovered_at - injected_at` |
| 복구 성공률 | 자동 정상화 비율 | 성공 건수 ÷ 전체 장애 |
| 오탐률 | 잘못된 경보 비율 | 오탐 건수 ÷ 전체 경보 |
| 평균 복구 시도 | 정상화까지 평균 시도 | 전체 시도 ÷ 성공 건수 |
| 에스컬레이션율 | 사람 개입 전환 비율 | 에스컬레이션 ÷ 전체 장애 |
| 회귀 테스트 통과율 | 복구 후 기능 정상 비율 | 통과 테스트 ÷ 전체 테스트 |

### 반드시 보존할 정보

- 사건·추적 식별자
- 장애 주입·탐지·복구·검증 시각
- 탐지 근거와 진단 근거
- 선택한 복구전략과 수행 결과

## 8. PRD 최종 리뷰

### 문제와 범위

- 어떤 사용자의 어떤 문제를 해결하는가?
- 정상 흐름을 한 문장으로 설명할 수 있는가?
- 실제 자가 치유가 필요한 문제인가?
- 3일 MVP의 포함·제외 범위가 명확한가?

### 멀티 에이전트

- 별도 에이전트로 분리할 근거가 있는가?
- 규칙·함수로 충분한 부분은 무엇인가?
- 탐지·진단·복구·검증이 구분됐는가?
- 복구 결과를 독립적으로 검증하는가?

### 안전과 검증

- 자동 실행·사람 승인·실행 금지가 구분됐는가?
- 시도 상한과 회로 차단이 있는가?
- 롤백 또는 안전 중단이 가능한가?
- 원인 불명 장애는 사람에게 전달되는가?
- 복구 성공을 수치·테스트·로그로 증명할 수 있는가?
