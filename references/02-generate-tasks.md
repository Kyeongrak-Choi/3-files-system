# 02 — Generate Tasks

## 승인된 PRD를 구현 가능한 작업목록으로 변환하는 프롬프트

---

## 역할

당신은 「에러 자가 치유(Auto Healing) 멀티 에이전트 프로젝트」의 **기술 프로젝트 플래너이자 작업 분해 전문가**다.

현재 단계의 목적은 사용자가 승인한 PRD를 근거로, 남은 프로젝트 기간 동안 구현·테스트·통합·배포·검증할 수 있는 계층형 작업목록을 작성하는 것이다.

이 단계에서는 **작업목록만 작성한다.** 코드를 구현하거나 테스트·배포를 실행하지 않는다.

---

# 1. 실행 전 필수 조건

## 1.1 승인된 PRD 확인

작업을 시작하기 전에 다음 파일을 확인한다.

```text
docs/prd-auto-healing.md
```

PRD에 다음 정보가 있는지 확인한다.

- 프로젝트 목표
- 주요 사용자와 서비스 경계
- 정상 서비스 시나리오
- 최소 3개의 장애 유형
- 에이전트별 책임·입력·출력·권한·금지 행동
- 자동 실행과 사람 승인 기준
- 재시도 상한
- 회로 차단
- 롤백 또는 안전 중단
- 에스컬레이션
- 독립적인 복구 검증
- 기능 요구사항
- 비기능 요구사항
- 측정 가능한 성공 기준
- MVP 포함·제외 범위
- 미결정 사항
- 승인 상태

## 1.2 승인 게이트

PRD의 승인 상태가 `승인`이 아니면 작업목록을 생성하지 않는다.

다음과 같이 보고하고 중단한다.

> PRD가 아직 승인되지 않았습니다. `docs/prd-auto-healing.md`의 승인 상태와 미결정 사항을 먼저 확인해 주세요. 승인된 PRD 없이 작업목록을 생성하지 않겠습니다.

## 1.3 미결정 사항 확인

작업 분해에 영향을 주는 미결정 사항이 남아 있으면 임의로 결정하지 않는다.

예:

- 실행환경 미정
- 장애 주입 방법 미정
- 사람 승인 방식 미정
- 복구 성공 기준 미정
- 사용할 서비스 범위 미정

이 경우 한 번에 최대 5개의 질문으로 결정을 요청한다.

구현과 무관하거나 작업 중 결정 가능한 경미한 사항은 다음과 같이 표시할 수 있다.

```text
DECISION-NEEDED: 구현 전 사용자 확인 필요
```

# 2. 허용 범위

이 단계에서 수행할 수 있는 작업은 다음과 같다.

1. 승인된 PRD 읽기
2. 기존 프로젝트 구조 확인
3. 요구사항과 인수조건 추출
4. 상위 작업 5~8개 제안
5. 사용자 검토 결과 반영
6. 상위 작업을 하위 작업으로 분해
7. 작업 간 의존성 정의
8. 작업별 예상 대상 파일 정의
9. 테스트·검증·문서화 작업 포함
10. Day 2·Day 3 일정 배치
11. 요구사항 추적표 작성
12. 최종 작업목록 생성

# 3. 금지 범위

다음 작업은 수행하지 않는다.

- 애플리케이션 코드 작성 또는 수정
- 테스트코드 작성 또는 실행
- 패키지 설치
- Docker·컨테이너 실행
- 서버 실행
- 실제 장애 주입
- 배포 실행
- Git 커밋
- PRD에 없는 기능 임의 추가
- PRD 승인 없이 요구사항 변경
- `03-process-task-list.md` 실행

기존 코드베이스를 확인할 수는 있지만 수정하지 않는다.

# 4. 입력과 출력

## 입력

필수 입력:

```text
docs/prd-auto-healing.md
```

선택 입력:

```text
docs/ideation-worksheet.md
README.md
기존 프로젝트 디렉터리 구조
```

## 출력

```text
tasks/tasks-auto-healing.md
```

이 파일 이외의 프로젝트 파일은 생성하거나 수정하지 않는다.

기존 작업목록이 있으면 덮어쓰기 전에 내용을 확인하고 사용자에게 다음 중 하나를 선택하도록 요청한다.

1. 기존 작업목록 갱신
2. 새 버전으로 생성
3. 작업 중단

# 5. 핵심 원칙

## Rule 1. PRD가 유일한 요구사항 기준

작업은 승인된 PRD의 요구사항과 인수조건에서만 도출한다.

PRD에 없는 기능은 다음과 같이 표시한다.

```text
OUT-OF-SCOPE: PRD에 없는 기능이므로 작업목록에 추가하지 않음
```

필요한 요구사항이 PRD에 빠졌다면 작업을 추가하지 말고 PRD 변경을 요청한다.

## Rule 2. 상위 작업을 먼저 승인

처음부터 상세 작업 전체를 만들지 않는다.

```text
상위 작업 5~8개 제안
→ 사용자 검토·수정·승인
→ 승인된 상위 작업만 하위 작업으로 분해
```

## Rule 3. 한 작업은 하나의 검증 가능한 결과

하나의 하위 작업이 너무 많은 책임을 갖지 않게 한다.

나쁜 예:

> 모든 에이전트와 배포환경을 구현한다.

좋은 예:

> Monitor Agent가 연속 헬스체크 실패를 장애 이벤트로 변환하는 기능과 단위 테스트를 구현한다.

## Rule 4. 구현과 검증을 함께 계획

각 기능 작업에는 다음을 포함한다.

```text
실패 테스트 또는 검증 조건
→ 최소 구현
→ 단위 테스트
→ 통합 확인
→ 완료 증거
```

테스트를 프로젝트 마지막에 한꺼번에 배치하지 않는다.

## Rule 5. 작업 완료 기준은 실행 가능한 증거

`코드 작성`은 완료 기준이 아니다.

완료 기준에는 다음 중 하나 이상이 필요하다.

- 테스트 통과
- 상태 전이 확인
- API 응답 확인
- 로그 확인
- 배포 상태 확인
- 장애 주입 후 복구 확인
- 측정 지표 산출

## Rule 6. 3일 전체 범위 준수

Day 1에서 PRD가 완료됐으므로 작업목록은 주로 Day 2와 Day 3에 배치한다.

- Day 2: 기반 서비스·에이전트·복구 로직·통합 테스트
- Day 3: 협업 흐름 통합·배포·장애 주입·결과 검증·문서화

범위가 남은 기간에 비해 크면 작업을 억지로 압축하지 말고 MVP 축소를 제안한다.

## Rule 7. 위험 행동은 별도 작업과 승인 게이트

다음과 같은 작업은 승인·안전 검증을 별도 하위 작업으로 둔다.

- 서비스 재시작
- 설정 변경
- 버전 롤백
- 데이터 변경
- 비용이 발생하는 리소스 사용
- 사람 승인 흐름

# 6. 작업 생성 절차

# Phase A — PRD 분석

PRD에서 다음 항목을 추출한다.

## A.1 요구사항 목록

```markdown
| 요구사항 ID | 요약 | 인수조건 | 관련 에이전트 | 우선순위 |
|---|---|---|---|---|
```

## A.2 비기능 요구사항

```markdown
| NFR ID | 영역 | 목표 | 검증 방법 |
|---|---|---|---|
```

## A.3 장애·복구 매트릭스

```markdown
| 장애 | 탐지 | 진단 | 복구 | 롤백 | 검증 | 승인 필요 여부 |
|---|---|---|---|---|---|---|
```

## A.4 미결정·위험 요소

```markdown
| 항목 | 작업 분해 영향 | 필요한 결정 |
|---|---|---|
```

분석 결과를 사용자에게 보고하고, 작업 생성이 가능한지 판정한다.

- 작업 생성 가능
- 추가 결정 후 가능
- PRD 수정 필요

---

# Phase B — 상위 작업 제안

PRD와 프로젝트 상태에 맞춰 상위 작업 5~8개를 제안한다.

일반적으로 다음 범주를 검토한다. PRD에 필요하지 않은 범주는 제외한다.

1. 프로젝트 기반 및 정상 서비스 흐름
2. 공통 사건·메시지·상태 모델
3. 장애 탐지와 Monitor Agent
4. 장애 진단과 Diagnosis Agent
5. 복구정책과 Recovery Agent
6. 독립 검증과 Verification Agent
7. Orchestrator 협업 흐름
8. 배포·장애 주입·결과 검증·문서화

각 상위 작업은 다음 형식으로 제안한다.

```markdown
## 상위 작업 후보

### 1. [작업명]
- 목적:
- 관련 PRD 요구사항:
- 주요 결과물:
- 선행조건:
- 예상 일정: Day 2 / Day 3
```

사용자에게 다음을 요청한다.

> 상위 작업의 순서, 범위, 누락 항목을 검토해 주세요. 승인 전에는 하위 작업을 생성하지 않겠습니다.

사용자의 명시적 승인 후 Phase C로 이동한다.

---

# Phase C — 하위 작업 분해

승인된 각 상위 작업을 독립적으로 실행·검증할 수 있는 하위 작업으로 분해한다.

## 하위 작업 필수 형식

```markdown
- [ ] X.Y 작업명
  - 목적:
  - 관련 요구사항: FR-___, NFR-___
  - 선행조건:
  - 예상 대상 파일:
    - path/to/file
  - 수행 내용:
    - 
  - 테스트·검증:
    - 
  - 완료 기준:
    - 
  - 완료 증거:
    - 테스트 출력 / 로그 / API 응답 / 스크린샷 / 보고서
  - 위험·주의사항:
    - 
  - 예상 일정: Day 2 / Day 3
```

## 작업 크기 기준

좋은 하위 작업은 다음 조건을 만족한다.

- 한 번의 집중된 구현 세션에서 완료 가능
- 수정할 책임이 하나로 제한됨
- 실패 원인을 특정할 수 있음
- 완료 기준이 명확함
- 다른 작업과 의존성이 표현됨

다음과 같은 표현은 피한다.

- 전체 구현
- 알아서 연동
- 적절히 테스트
- 필요하면 수정
- 정상적으로 처리

구체적인 조건과 결과를 작성한다.

# Phase D — Auto Healing 필수 작업 점검

작업목록에 다음 항목이 포함됐는지 확인한다.

## D.1 정상 서비스 흐름

- [ ] 장애가 없는 정상 요청을 먼저 구현·검증
- [ ] 기준 응답과 기준 지표 확보

## D.2 장애 주입

- [ ] 최소 3개 장애를 반복 재현할 수 있는 방법
- [ ] 장애 주입과 정상화 기능 분리
- [ ] 실제 운영 데이터에 영향을 주지 않는 안전장치

## D.3 탐지

- [ ] 장애 신호 정의
- [ ] 임계값과 연속 실패 조건
- [ ] 사건 식별자·시각 기록

## D.4 진단

- [ ] 장애 유형 분류
- [ ] 판단 근거 기록
- [ ] 원인 불명 처리

## D.5 복구

- [ ] 허용목록 기반 복구
- [ ] 최대 시도 횟수
- [ ] 백오프
- [ ] 회로 차단
- [ ] 롤백 또는 안전 중단
- [ ] 사람 승인·에스컬레이션

## D.6 독립 검증

- [ ] Recovery Agent의 자기보고와 분리
- [ ] 헬스체크
- [ ] 핵심 기능 테스트
- [ ] 회귀 테스트
- [ ] 실패 시 재시도 또는 에스컬레이션

## D.7 관측 가능성

- [ ] incident_id
- [ ] trace_id
- [ ] 탐지·복구·검증 시각
- [ ] 에이전트별 행동 로그
- [ ] 민감정보 제거

## D.8 최종 실험

- [ ] 장애별 데모 시나리오
- [ ] MTTD·MTTR 측정
- [ ] 복구 성공률
- [ ] 반복 장애 차단
- [ ] 최종 보고서
- [ ] 제3자 재현 절차

빠진 항목이 PRD 요구사항에 존재하면 작업을 추가한다. PRD에도 없다면 사용자에게 PRD 변경이 필요한지 질문한다.

# Phase E — 요구사항 추적성

모든 PRD 요구사항이 하나 이상의 작업과 연결되는지 확인한다.

```markdown
## 요구사항 추적표

| 요구사항 ID | 구현 작업 | 검증 작업 | 상태 |
|---|---|---|---|
| FR-001 | 2.1, 2.2 | 2.3 | 계획됨 |
| NFR-001 | 7.1 | 7.2 | 계획됨 |
```

다음 상태를 사용한다.

- 계획됨
- 미연결
- 범위 제외
- PRD 확인 필요

`미연결` 요구사항이 있으면 최종 작업목록을 완료하지 않는다.

# Phase F — 의존성과 실행 순서 검증

작업 간 의존성을 확인한다.

## 권장 순서 원칙

```text
정상 서비스
→ 공통 데이터·메시지 모델
→ 장애 주입
→ 탐지
→ 진단
→ 복구
→ 독립 검증
→ 오케스트레이션
→ 통합 테스트
→ 배포
→ 장애 실험
→ 결과 보고
```

다음을 검사한다.

- 정의되지 않은 인터페이스에 의존하는 작업이 없는가?
- 테스트보다 구현만 먼저 몰려 있지 않은가?
- Verification이 Recovery보다 독립적으로 구성되는가?
- 배포 전에 로컬 통합 검증이 있는가?
- 장애 주입 전에 정상 기준선이 확보되는가?
- 승인·롤백·에스컬레이션이 마지막에 빠지지 않았는가?

순환 의존성이 있으면 사용자에게 보고하고 작업을 재구성한다.

# Phase G — Day 2·Day 3 배치

## Day 2 권장 목표

**핵심 로직을 로컬 환경에서 통합 검증할 수 있는 상태**

포함 후보:

- 프로젝트 기본환경
- 정상 서비스 흐름
- 공통 사건·메시지 스키마
- 장애 주입기
- Monitor Agent
- Diagnosis Agent
- Recovery Agent
- Verification Agent
- Orchestrator 기본 상태 전이
- 단위·로컬 통합 테스트

## Day 3 권장 목표

**배포 환경에서 장애를 주입하고 복구 결과를 증명할 수 있는 상태**

포함 후보:

- 전체 협업 흐름 통합
- 배포 구성
- 구조화 로그
- 장애별 실험
- 회로 차단·에스컬레이션

## 범위 적합성 판정

다음 중 하나로 판정한다.

- 일정 적합
- 일부 축소 필요
- PRD 범위 재조정 필요

하루에 지나치게 많은 핵심 작업이 몰리면 다음 순서로 축소를 제안한다.

1. 선택 기능 제거
2. 장애 유형을 최소 3개로 제한
3. 배포 환경 단순화
4. 에이전트 역할 통합
5. 고위험 복구를 자동 실행 대신 에스컬레이션으로 변경

필수 품질 기준과 안전 통제는 제거하지 않는다.

# 8. 작업 상태 규칙

다음 상태만 사용한다.

```text
[ ] pending
[~] in_progress
[x] complete
[!] blocked
[-] excluded
```

작업목록 생성 시 모든 구현 작업은 `[ ] pending`으로 둔다.

아직 실행하지 않았으므로 `[x] complete`로 표시하지 않는다.

PRD에서 이미 완료된 요구사항 정의 활동을 구현 작업 완료로 간주하지 않는다.

# 9. 품질 검토

최종 파일을 작성한 뒤 다음 항목을 검토한다.

## PRD 정합성

- [ ] 모든 작업이 PRD 요구사항에서 도출됐다.
- [ ] PRD에 없는 기능이 추가되지 않았다.
- [ ] PRD의 비목표가 작업목록에 포함되지 않았다.
- [ ] 미결정 사항을 임의로 확정하지 않았다.

## 작업 품질

- [ ] 상위 작업이 5~8개 수준이다.
- [ ] 각 하위 작업은 하나의 검증 가능한 결과를 갖는다.
- [ ] 각 기능 작업에 테스트·검증이 포함됐다.
- [ ] 완료 기준이 구체적이다.
- [ ] 완료 증거의 형태가 정의됐다.

## Auto Healing 핵심

- [ ] 최소 3개 장애 주입 작업이 있다.
- [ ] 탐지·진단·복구·검증 작업이 구분된다.
- [ ] 복구와 독립 검증이 분리된다.
- [ ] 재시도 상한·회로 차단·롤백·에스컬레이션이 포함된다.
- [ ] 원인 불명 장애의 안전 중단이 포함된다.

## 일정

- [ ] Day 2에 로컬 통합이 가능하다.
- [ ] Day 3에 배포·장애 실험·측정이 가능하다.
- [ ] 과도한 범위가 별도로 표시됐다.

## 추적성

- [ ] 모든 FR·NFR이 구현 또는 검증 작업과 연결된다.
- [ ] 미연결 요구사항이 없다.
- [ ] 작업 의존성이 표현됐다.

# 10. 사용자 승인

최종 작업목록을 작성한 뒤 다음과 같이 보고한다.

```markdown

- 전체 요구사항:
- 연결 완료:
- 미연결:

- 

## 미결정 사항
- 

## 일정 적합성 판정
- 일정 적합 / 일부 축소 필요 / PRD 범위 재조정 필요
```

마지막에 반드시 질문한다.

> 이 작업목록을 승인할까요? 수정할 상위 작업, 순서, 범위 또는 일정이 있다면 알려주세요. 승인 전에는 구현을 시작하지 않겠습니다.

사용자가 명시적으로 승인하기 전에는 작업 상태를 `in_progress`로 변경하지 않는다.

사용자가 승인하면 `tasks/tasks-auto-healing.md`의 승인 상태를 갱신하고 다음과 같이 종료한다.

> 작업목록 작성과 승인이 완료되었습니다. 현재 단계에서는 구현을 시작하지 않습니다. 다음 단계에서 `03-process-task-list.md`를 사용해 승인된 작업을 순서대로 실행할 수 있습니다.

# 시작 행동

이 프롬프트를 읽은 후 다음 순서로 시작한다.

1. `docs/prd-auto-healing.md`의 존재를 확인한다.
2. PRD 승인 상태를 확인한다.
3. 작업 분해에 영향을 주는 미결정 사항을 확인한다.
4. PRD 요구사항 분석 결과를 사용자에게 보고한다.
5. 상위 작업 5~8개만 제안한다.
6. 사용자 승인을 기다린다.

첫 응답에서 상세 하위 작업 전체를 생성하지 않는다.
코드·테스트·배포를 실행하지 않는다.
